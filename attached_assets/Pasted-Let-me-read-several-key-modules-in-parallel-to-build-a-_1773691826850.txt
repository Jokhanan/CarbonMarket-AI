Phase 2 — Product Intent
What this platform is trying to be
CarbonGPT is attempting to solve a real, high-friction problem: the process of developing a carbon credit project from concept to verified credits is slow, manual, expert-intensive, and error-prone. It typically requires a team of carbon consultants, months of document writing, and expensive validation bodies.

The platform is simultaneously:

1. A carbon project development studio — Guides a developer from selecting a methodology through writing a compliant PDD, managing the crediting period, and producing monitoring reports. The AI draft-and-review loop is the core value proposition here.

2. An emission reduction calculation engine — Provides methodology-specific ER calculators that are auditable (Excel workbook with live formulas, no hardcoded values). This is critical for credibility with validators.

3. A knowledge infrastructure — The Methodology Pack Manager, knowledge base, TOOL33 defaults, and research orchestrator represent a growing proprietary dataset of methodology intelligence that gets better the more projects use it.

4. A market intelligence terminal — The Carbon Intelligence module (registry sync, country explorer, methodology analysis, project browser) tries to give users a Bloomberg-like view of the carbon market.

5. An audit preparation tool — The audit simulator, evidence engine, and findings response assistant help developers anticipate what validation bodies will challenge, and prepare defensible responses.

The platform's vision is clear: reduce the time and cost of carbon project development by 70–80% through AI automation, while maintaining the rigour and traceability required by Gold Standard and Verra VCS validators.

Phase 4 — AI Integration Analysis
Current state: Reactive assistant, not proactive copilot
The AI currently acts when the user explicitly asks it to act. It is an excellent tool but not yet a true partner. Key observations:

What the AI does well:

Section drafting with rich context (parameters + ER results + documents + methodology knowledge)
Intelligence extraction from uploaded PDFs (structured parameter values, project metadata)
Audit simulation with parameter/evidence/consistency checks
Findings response drafting (CAR/CL/FAR with regulatory precision)
Copilot chat with function-calling for direct actions
The biggest missed AI opportunities:

1. Proactive parameter suggestion. When a user uploads a PDD from a comparable project, the system extracts intelligence but only surfaces it in the Intelligence Review tab. The AI should proactively offer: "I found fNRB = 0.82 in the uploaded document. This matches your project country. Should I apply it?"

2. Cross-project benchmarking. The methodology packs contain real PDDs from approved projects. The AI could compare a user's parameters to the pack's distribution — "Your fNRB of 0.30 is below the median of 0.68 for VM0050 projects in Sub-Saharan Africa. This will likely draw a CL from the VVB."

3. Automatic ER narrative generation. After running a scenario, the AI should offer to write the ER section immediately, pre-filled with the actual scenario output, not a generic draft.

4. Continuous consistency validation. As the user edits parameters and drafts sections, the AI should flag contradictions in real time — "Your Parameters tab shows 5,000 households but your drafted A.4 section mentions 3,000."

5. Additionality automation. The research orchestrator gap-fills project-level fields but doesn't automate the additionality test. This is the hardest and most contested section in any PDD — the AI should run through the investment/barrier/first-of-its-kind test and produce a structured argumentation.

6. The Copilot is under-utilized. It can create projects, run simulations, and draft sections via chat. But it doesn't proactively surface insights — it only responds. A truly proactive copilot would open the workspace and say "Your Parameters tab has 6 missing values that will block section drafting. Here's what each one is and where to find it."

7. No AI in the Export tab. The export produces a compliant document, but there's no AI pass that checks the final document for internal consistency, missing table references, or formatting issues before the user downloads it.

Known Calculation Issues
Issue 1 — VM0050 electric/LPG stove devices: Parameters EC_electricity_project, EF_electricity, and TDL are defined in the parameter engine and shown to users, but calculate_cookstove_er uses project_fuel_consumption for all project types. The electricity-based formula path (VM0050 Eq. 8) is not implemented in the calculator. Users with electric cookstove projects will get wrong results silently.

Issue 2 — MECD workbook: The MECD calculation steps have no canonical_key field, so the Excel workbook generates a Parameters sheet but the Calculation sheet is populated only with static values (no live formula references to the Parameters tab). This breaks the "fully traceable workbook" guarantee for MECD.

Issue 3 — Grid year-table col 3 fallback: In er_excel.py, when eg_pj_cell is None for a grid project year row, the fallback formula computes baseline_emissions / baseline_emissions which equals 1.0 instead of the actual EG_PJ value. This would produce wrong year-table results for grid projects where the electricity generation cell reference is missing.

Issue 4 — TPDDTEC cohort + method_id: calculate_cookstove_er_cohort accepts method_id but the cohort engine's per-unit emission chain at line ~565 references a comment "same canonical structure as calculate_cookstove_er" — this needs validation that Method 2 locked default and Method 3 fuel-switch logic propagate correctly through the cohort wrapper.

Calculation Strengths
The 8-step canonical chain (baseline_fuel_consumption → bl_consumption_wood_equiv → baseline_energy_tj → baseline_emissions_per_device → project_energy_tj → project_emissions_per_device → er_per_device_before_leakage → net_er_annual) is correctly structured per VM0050.
fNRB is correctly applied to baseline only for Method 3, not to project emissions — per methodology specification.
The CF (wood-to-charcoal conversion factor) chain is correctly handled for charcoal baseline fuels.
The Excel workbook formulas are genuinely live — every =Parameters!C{row} reference updates when the parameter changes.

Phase 7 — What is Missing for an Excellent Product
Missing: Workflow intelligence
The platform knows a lot about each project but never synthesizes that knowledge into a unified project health narrative. Users should be able to see, at a glance:

"Your project is at Validation Preparation stage. 3 critical parameters are missing. Once set, your ER estimate will finalize and I can draft the remaining 4 sections."
Currently this information exists but is scattered across 4 different tabs.

Missing: Automated additionality support
Additionality is the most contested, most subjective, and highest-risk section of any PDD. The platform drafts it with the AI but doesn't provide structured support for: investment test, barrier analysis, common practice test, or first-of-its-kind documentation. Validators flag this more than any other section.

Missing: Comparable project benchmarking
The methodology packs contain real approved PDDs. The platform could automatically pull parameter ranges from comparable projects (same country, same methodology, same scale) and show: "For VM0050 cookstove projects in Kenya, fNRB typically ranges 0.68–0.82. Your value of 0.30 is an outlier." This would preempt a huge number of validator challenges.

Missing: Real-time cross-section consistency
When a user edits a parameter or approves a new ER scenario, affected draft sections should be flagged as potentially stale. The validate_document_consistency function exists in ai_writer.py but is only invoked manually.

Missing: Carbon market data integration
The Carbon Intelligence module has analytics from registry-imported project data, but no live price feeds, no credit issuance tracking against similar projects, no forward vintage pricing. For a platform targeting finance-oriented users, this is a significant gap.

Missing: Validation body perspective mode
The audit simulator simulates a VVB audit, but the output is a readiness score and a list of issues. What's missing is a "validator view" — a report formatted the way a VVB would write it (with CAR numbers, finding categories, and regulatory citations) so the developer can see exactly what will happen when they submit.

Missing: Guided parameter determination workflows
For each parameter that requires a tool calculation (fNRB from TOOL30/TOOL33, grid EF from TOOL07, leakage from tool library), the platform should offer a step-by-step in-app calculator that walks the user through the referenced tool and stores the result with its derivation trace. Currently users must do this in a spreadsheet and manually enter the result.

Summary Assessment
CarbonGPT has genuinely strong bones. The calculation engine is methodologically rigorous. The knowledge infrastructure (methodology packs, TOOL33 defaults, research orchestrator) is a real competitive moat. The AI writing quality, when properly contextualized, produces credible first drafts.

Workflow fluidity — the system knows everything it needs to act proactively but waits to be asked

The platform is at the transition point between "powerful tool for carbon experts" and "intelligent copilot for carbon project developers." The roadmap above is the path from one to the other.

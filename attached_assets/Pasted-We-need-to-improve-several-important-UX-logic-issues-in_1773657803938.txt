--------------------------------------------------
PART 1 — PROJECT PARAMETERS CLEANUP
--------------------------------------------------

There is confusion and duplication in the parameter forms.

Current issue examples:
- "Project Fuel Consumption Rate" is entered in kg/device/day
- "Project Annual Fuel Consumption" is entered in t/device/year
These are the same underlying quantity expressed in different units.

Similarly:
- baseline fuel consumption is shown in kg/device/day
- baseline annual fuel consumption is shown in t/device/year
- the app appears to hardcode a household size of 5 in some calculations instead of using the selected household size field

This is confusing and bad UX.

Please audit the current parameter logic and implement the following:

1. Define one canonical quantity for each concept.
   Example:
   - raw daily rate (kg/device/day)
   - derived annual consumption (t/device/year)

2. The user should NOT need to manually enter both when one can be derived safely.

3. If the user enters kg/device/day, the annual value should be derived automatically.
   If the user enters annual consumption, the daily value should be derived automatically.
   Keep them synchronized.

4. Remove hardcoded household size assumptions.
   If annual household consumption depends on household size, use the actual selected household_size field, not a hardcoded 5.

5. Reorganize the parameter form so that the drivers appear before the derived values.
   Example:
   - household size
   - devices per household
   - baseline/project fuel type
   - daily consumption
   - derived annual consumption

6. Clearly label:
   - user input fields
   - auto-derived fields
   - default values
   - methodology-based values

The objective is to reduce duplicate input and make the logic transparent.

PART 2 — SDG LOGIC CLEANUP
--------------------------------------------------

Current SDG handling is not well structured.

Problems:
- SDG 13 is being entered manually even though it should be derived from emission reductions
- SDG 1 and SDG 15 can also be partly derived from other quantities
- users are being asked too early for values they do not yet know

Please redesign SDG handling safely.

Implement the following logic:

1. SDG 13 should be derived automatically from calculated emission reductions.
   The user should not manually enter the emissions reduction again inside SDG.

2. SDG 15 (for biomass/forest-related projects) should be derivable from biomass saved, where possible.

3. SDG 1 (household savings) should be derivable where possible from:
   - biomass/fuel saved
   - fuel price
   If fuel price is unknown, allow user override + source.

4. Keep manual override capability for all SDG values, but clearly mark whether the value is:
   - calculated
   - defaulted
   - user override

5. Move SDG entry to a later logical stage if needed, after key calculations exist.

6. Make it clear which SDGs are:
   - automatically derivable
   - partially derivable
   - fully manual

PART 3 — PROJECT SCALE AUTO-DETECTION
--------------------------------------------------

Current project scale selection is too manual.

Please audit the methodology logic and implement safer scale handling.

Requirements:

1. Determine where project scale can be auto-detected from:
   - calculated ER
   - methodology thresholds
   - project type / fuel / technology
   - user-entered quantities

2. If scale can be inferred, auto-suggest it or auto-fill it.

3. If scale is uncertain, show the detected suggestion and allow override.

4. Do not require users to manually choose scale when the app can derive it logically.

Please design and implement a first version of this.
